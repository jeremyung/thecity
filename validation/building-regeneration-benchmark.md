# Building regeneration benchmark

This benchmark answers the follow-up question for the indexed source-retention plan: what CPU work is needed to recreate authored groups for the same city and rebuild their spatial batches? It uses the production `buildingKit()`, `ArtMaterials`, and `BuildingChunks` on the 850-building seed **87231**, tick **242000** snapshot (`early-reservation-wasm-87231-snapshot.json`, SHA-256 `0559e20d76403429dffcc8a13d0953b699accf0ce2c73df0e30401c4da40c94f`). Run `node scripts/benchmark-building-regeneration.mjs` to reproduce.

The benchmark warms the complete city once, then regenerates every occupied 200 m chunk four times. It separates three production stages: `buildingKit()` generation; source preparation (`position`/rotation plus `BuildingChunks.set()`, including outline extraction); and `BuildingChunks.update()` batch transformation/merge. Every sample disposes its batch and authored groups before proceeding. This is CPU-side Node wall time, not browser/GPU time.

Across 64 measured chunk samples (16 chunks × 4 repeats), authored group generation took **78.8 ms median, 174 ms p95, 200 ms maximum per chunk**. Source preparation took **192 ms median, 451 ms p95, 566 ms maximum**. Batch transformation/merge took **19.2 ms median, 36.5 ms p95, 56.9 ms maximum**. The earlier benchmark version attributed `set()` outline extraction to transform/merge; this report measures it separately. Per-chunk samples, including counts and four timings, are in the JSON report.

These measurements argue against rebuilding an entire dirty chunk synchronously inside `update()`. In the live renderer, group generation and `set()` preparation are currently spread across the bounded two-buildings-per-frame queue; they are chunk totals here, not one-frame latency. A retained-source removal must preserve that staged discipline when a later dirty chunk regenerates descriptors. The current `update()` transformation/merge is a single synchronous commit and measured 19.2 ms median / 56.9 ms maximum, so it also needs bounded staging for large replacements. Keep the old batch visible; author and prepare a small number of sources per frame, then transform/partition them and fill final per-material output buffers in bounded slices before swapping the completed batch. A single final `mergeGeometries()` is not a safe last step for these chunk sizes; use incremental output-buffer assembly or sub-batches, with picking spans kept in the same stable face order. Dispose each temporary authored group after its transformed attributes are copied. Retire the old batch through the renderer's existing delayed-disposal path after replacement commits.

The host was macOS 25.6, Apple M2 Max (arm64, 12 logical CPUs), Node 26.7.0, 32 GiB RAM. The OS reported about **1.39 GiB free RAM** before this run, and the process was not isolated from other work. Repeat under controlled load before setting quotas. The numbers show that whole-chunk synchronous regeneration/merge is unbounded relative to a frame; they are not a frame-budget calibration. No browser memory, GPU memory, visual quality, or frame rate was measured.

The full machine/runtime and source-code hashes are recorded in [`building-regeneration-benchmark.json`](./building-regeneration-benchmark.json); the script is [`benchmark-building-regeneration.mjs`](../scripts/benchmark-building-regeneration.mjs). The array-byte savings estimate remains in [`mature-building-geometry-budget.md`](./mature-building-geometry-budget.md); this timing run does not measure runtime memory release.
